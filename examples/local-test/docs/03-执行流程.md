# 03 · 执行流程

> 一条笔直的主线:从你在终端敲 `pnpm dsh web` 开始,到模型回话、工具执行,再到这一轮结束。分三节:**启动** / **插件树组装** / **对话 Turn-Step 循环**。

## 一、启动链路

```
pnpm dsh web --profile web ...
   │
   ▼
node --import tsx/esm apps/cli/src/bin.ts     # dsh bin(tsx ESM hook)
   │
   ▼
parseDshArgs(process.argv.slice(2), version)  # args.ts → 得出 invocation.mode
   │
   ├─ mode === 'profile' ──► runProfile({...})        ← 大多数情况走这里
   ├─ mode === 'plugin'  ──► runPlugin(profile, args)  ← dsh plugin
   ├─ mode === 'dump-config' ▸ runDumpConfig(...)
bin.ts 按 mode 动态 import(promise 不被打进不相干的分支)
```

`.nvmrc` → Node v22.23.2 约定;`loadLayeredEnv` 从 `process.env > .env > ~/.env` 装环境(凭据解析器 boot 前就需要)。

## 二、插件树组装(`apps/cli/src/profile-boot.ts`)

这是整个项目最「核心」的一段 —— 所谓「一切皆插件」,机制上就是 **一层层 config patch 叠进空根**。

```
runProfile(options)
  │
  ├─ composeProfile(name, patches)
  │     prepareProfile(name)              # loadProfile(...) + 重写空根 cordis.yml
  │     homePatches = $DSH_HOME/cordis.patch.yml
  │     overlays   = --patch overlay 文件
  │     bundlePatches = profile.layers.flatMap(layer => layer.patches)
  │     rows = composeEntries([bundlePatches, profile.patches, homePatches, overlays])
  │     + agent-presets root + telemetry 开关 patch
  │
  ├─ 装进程级 shutdown(SIGTERM→0 / SIGINT→130) + installFailLoud
  │
  ├─ boot(NAME, rootConfig, allPatches, hostCtx => {
  │       hostCtx.provide(DSH_LAUNCH_ENVIRONMENT_KEY, env)  # 任何内容 mount 之前,先冻结启动环境
  │       provideCmdline(hostCtx, { args, exit })            # 注入调用方参数
  │   })
  │
  └─ boot() 之后的「热更兜底」:
       若 loader 活着且没退出: 缺 timer→挂 cordis-plugin-timer; 缺 hmr→挂 cordis-plugin-hmr
       watchUserPatches(profile patch 层 + home patch 层)   # cordis.patch.yml 编辑即热更
```

**patch 叠加顺序(低→高,高的覆盖低的同 id row):**
```
空根 [] ← bundle1 patches ← bundle2 ... ← profile.cordis.patch.yml ← $DSH_HOME 用户层 ← --patch overlays ← telemetry
```
一个 patch 按 row 的 `id` 定位并**整体替换**它的 config,或插入新 row。`--dump-config` 就是把这些层算出来打印 —— 你看到的每一行都能被自己的 patch 覆盖。

`boot()`(来自 `@deepseek-ai/dsh-app-boot`)最后落在 vendored **Cordis Loader** 上:把整棵 entry list 喂给 Loader,Loader 按每个插件的 `inject` 依赖解析加载顺序,把每个插件 `apply(ctx)` 进同一个根 `Context`。`ctx` 从此成为一个服务仓库。

## 三、对话 / 任务的 Turn-Step 循环

`web` profile 里 `dsh-web-app` bundle 拉起了 Web 服务(`ctx.web`/HTTP server);用户聊天消息进来,进入 `core/agent-loop` 实现的驱动。核心抽象是**两个单位**:

> **step** = 一次模型请求 + 它调用的工具。
> **turn**  = 零或多个 step:在第一次输入被 claim 前打开,到「没有欠着的事」才关闭。

### 一次 step 的完整走法

```
turn/start
  claim 下一次 step 输入 + 1 条排队消息
  assemble 提示词分节 + 工具 schema(system-prompt 组装)
  │
  └─► agent/pre-step【waterfall】        可重写 claim 的消息或直接 reject
         │   reject / 首个 enter 被重写成空 → turn 关闭且没花 step(日志仍记录“那一次尝试”)
         ▼
     step/start
       append enter 的消息为 user/message(SessionEvent)
       derive model history from log        # 模型看到的上下文 = 从 SessionLog 投影
       │
       ├─► agent/request【waterfall】→ llm/stream【waterfall】→ assistant/chunk* → assistant/message
       │
       └─► tool/call*
             └─► tools/pre-execute【waterfall】→ tools/execute【waterfall】→ tools/post-execute【waterfall】→ tool/result*
       step/end
       还欠一个模型请求 / 又有 next-step 输入 → claim → 下一 step
  │
agent/turn-stopping【serial, 无 next】
turn/end
```

**哪些是「持久化事实」、哪些是「活的扩展点」—— 三域分工:**

| 事件 | 域 | 持久到 Session Log? |
|---|---|---|
| `turn/*`, `step/*`, `user/message`, `assistant/*`, `tool/*` | 会话 | ✅ 是(可重放、fork、续聊、遥测都从这流派生) |
| `agent/*`(pre-step/request/turn-stopping/inbox/status/value/continuation) | agent | ❌ live 节点,携带活 `Agent` |
| `fs/*`, `tools/*`, `telemetry/*` 等 | capability | ❌ 给 seam 挂策略/适配器,不 import 循环 |

**waterfall 语义(必须 get):** 监听器收 `(...args, next)`。调用 `next()` 才往下委派(可能被包装/改写的结果传下去),不调用就短路。`agent/pre-step`、`agent/request`、`llm/stream`、三个 `tools/*` 都是 waterfall;`agent/turn-stopping` 是 serial 且**没有** `next()`。

**一条铁律:** 模型能看到的东西 ⟺ 必须能由 Session Log 重建。所以任何新的「模型可见输入」都要先加一个 `SessionEvent`,再从日志渲染,运行时有一个不变量在 assert 这件事。这就是为什么 `SessionEventMap` 的扩展要小心。

### 输入如何进来

模型驱动通过**一个 inbox** 收输入。有些消息(用户新消息、工具结果)会立刻唤醒它;被注入的上下文(`agent.inject()`)则先排队,等另一条消息来……这种「注入上下文. 等在 inbox 里直到别的消息唤醒」的设计,是 `agent/*` 事件和 `inject()` 存在的原因。

## 四条会经常用到的终点 (`docs/architecture.md` 原表节选)

| 想要 | 机制 |
|---|---|
| 加模型 provider | 在 `ctx.llm` 注册适配器 |
| 加模型可见能力 | 在 `ctx.tools` 注册(其 schema 进提示词组装) |
| 给某会话不同能力集 | 组一个 agent preset |
| 拦截一次请求/工具/turn | 用它的 `agent/*` 或 `tools/*` 事件;`agent/turn-stopping` 停一个 turn |
| 加模型可见上下文 | `agent.inject()` → 落到下一次 admissions 的 request |
| 加持久会话状态 | 扩展 `SessionEventMap`,从日志渲染/重放 |

## 端到端时间线(web,带 key)

```
1. 终端        pnpm dsh --profile web
2. bin.ts      mode=profile → runProfile
3. profile-boot  解析 web profile → 叠 patch → boot()
4. Loader      按 inject 依赖逐个 apply 所有插件(含 base bundle 的模型/工具/持久化)
5. web bundle  拉起 ctx.web HTTP 服务 → 127.0.0.1:3080
6. 用户在 UI 发消息
7. agent-loop  turn/start → claim → agent/pre-step → step/start
8.             derive 历史 → agent/request → ctx.llm stream(DeepSeek provider)→ assistant/chunk*
9.             触发工具 → tools/execute(pre/post)→ tool/result* → step/end
10.            还欠?继续 step;不欠 → agent/turn-stopping → turn/end
11. UI 从 session/event 渲染回复;Session Log 追加所有持久事实
12. CTRL-C → SIGINT→130 → 整树 dispose → 进程退出
```

> 一句话总结执行流程:**命令行 → profile-boot 把「profile/bundle/patch」层叠成插件树 → Loader 按依赖 apply 进一个 Context → agent-loop 在 Session Log 之上跑 turn/step 循环 → 每个能力都是事件 seam,每个求值都过 waterfall。**
