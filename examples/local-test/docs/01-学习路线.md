# 01 · 从零学习路线

> 目标:一个没有任何本仓库背景的人,按这条路线走完,能读懂 `packages/` 下的代码、写出自己的插件、跑通测试,并且知道该查哪些文档。
> 每阶段都给了:学什么 / 读什么(仓库路径)/ 怎么验证自己学会了。

前提(你的机器):Node.js `^22.19 || >=24`(本机约定用 **v22.23.2**,见记忆,默认 v20 会破坏 zstd 和 pnpm)、Corepack 开着的 pnpm(`pnpm --version` ≈ 11.x)、TypeScript 基础、git。

---

## 阶段 0 · 把项目跑起来(半天)

动手跑之前先对「这是什么」有个直觉。

**读:**
- 仓库根 `README.md` / `README.zh.md` —— 项目一句话定位。
- `apps/cli/src/bin.ts` —— CLI 入口,先看 `switch (invocation.mode)` 那几行,知道有 profile / plugin / dump-config 三种模式。

**做 + 验证:**
```sh
pnpm install          # 装依赖(同时装好 lefthook hooks)
pnpm run typecheck    # 首次 clone 后必须成功
pnpm run build        # 产出 lib/ 供 dsh 使用
pnpm dsh --profile headless "用一句话介绍你自己"   # 需要 DEEPSEEK_API_KEY(或根 .env)
pnpm dsh --profile web --dump-config    # 打印你机器上实际会启动的插件树——这是理解全局的关键命令
```

✅ **验收**:`dump-config` 能看到一长串 id 列表(`dsh-web-app`、`dsh-base` 里的各种 row),说明你已经摸到了「插件树」这扇门。

---

## 阶段 1 · 吃透 Cordis 框架(1~2 天)

**这是整个项目的思维地基,没有捷径。** 先读 primer,再做 tutorial(教程共 7 章,边写边改 `examples/local-test` 下的脚手架验证)。

**读:**
- `docs/cordis-primer.md` —— 「五句话讲清 Cordis」+ 四种事件分发模式(emit/waterfall/parallel/serial)+ waterfall 语义 + Loader 配置。
- `docs/cordis-tutorial/index.md` 及 `0?` 各章:
  - `01-first-plugin` 首个插件
  - `02-lifecycle-and-effects` 生命周期与副作用(注册即效果,可回滚)
  - `03-services` 服务(`ctx.<key>` + `inject`)
  - `04-events` 事件
  - `05-config` 配置(config + `!!js`)
  - `06-composition-and-hmr` 组合与热更新
  - `07-into-the-harness` 走进 harness
- 术语看 `docs/glossary.md`(`capability seam`、`Service Definition/Provider/Consumer`)。

**现场脚手架**(本仓库已带):`examples/local-test/cordis.yml` + `probe.ts` + `debug-driver.ts`。它们本来就为调试 `vendor/cordis/src/context.ts` 写的;**在 `context.ts` 的构造函数或 `Context.prototype.provide` 打断点**,跑 `debug-driver.ts` 就能看到插件 apply 被调用 —— 这是理解「上下文/插件/效果」最好的现场。

**做:** 在 tutorial 每章末尾,自己往 `cordis.yml` 加一个 `!!js` 表达式、或写一个 `ctx.provide` + 一个 `ctx.waterfall`/`ctx.on` 监听,观察它们如何被 HMR 热更。

✅ **验收**:你能说出 —— 「为什么新增能力不用改 main()?」「为什么监听器回调有 next,不调用会怎样?」「ctx.waterfall 和 ctx.on 的语义差别」。
要求:assert「一个插件服务靠 `inject` 声明依赖,而不是手动排启动顺序」。

---

## 阶段 2 · 组装:profile 与 bundle(1 天)

理解了插件本体,再理解「怎么把它们拼成一台能跑的机器」。

**读:**
- `docs/architecture.md` 的「Profiles and bundles」小节。
- 真正动手:对比 `dump-config` 的输出和你两个 profile 的 bundle 定义。
- bundle 第一层:`packages/bundle/base/README.md`(`dsh-base` —— 每个 profile 都有的模型适配、工具、持久化、沙箱、审批、设置、凭据、遥测);`packages/bundle/web-app/README.md`(加上浏览器应用);`packages/bundle/headless/README.md`(无服务端的单次 runner)。
- 组成机制:`packages/boot/app-boot/README.md`(profiles 小节)。

**关键概念:** layered patch。空 config → 按 `dsh.profile.bundles` 顺序叠每层的 `cordis.patch.yml` → profile 自己的 patch → `$DSH_HOME` 用户层 → `--patch` overlay。patch 按 row 的 id 定位并整体替换。

✅ **验收**:能解释「给某个 row 打 patch」会发生什么、谁会覆盖谁。命令:`pnpm dsh --profile web --dump-config`。

---

## 阶段 3 · 核心子系统(2~3 天,主线)

现在读主干,顺序按「数据流方向」走:日志 → 提示词 → 工具 → agent → 循环 → LLM。

**读(都是 `docs/subsystems/` 下的页 + 对应包源码):**
| 子系统 | 文档页 | 包 | ctx 键 | 装什么 |
|---|---|---|---|---|
| Session 日志 | `session.md`, `session-projection.md` | `core/session` | `ctx.sessions` | 追加式 `SessionEvent` 日志 + 内存态 |
| System Prompt | `system-prompt.md` | `core/system-prompt` | `ctx.systemPrompt` | 提示词分节 + 工具 schema 组装 |
| Tools | `tools.md`, `tool-execution-pipeline.md` | `core/tools` | `ctx.tools` | 作用域式工具注册 + 守卫执行管线 |
| Agent | `core.md` | `core/agent` | `ctx.agents` | Agent 接口/注册表/`agent/*` 事件 |
| Agent Loop | `core.md` | `core/agent-loop` | `ctx.agentLoop` | 实现 Agent 接口的默认驱动 |
| Scope | `scope.md` | `core/scope` | 无 | 每 agent 作用域的注册原语 |
| LLM | `llm-streaming.md` | `llm/llm` | `ctx.llm` | 消息/流词表 + 适配器 seam |

**同时读:** `docs/architecture.md` 的「Events」「Session log」「Turn flow」三节 —— 这是整棵树的骨架。

✅ **验收**:对着 `docs/architecture.md` 里的 turn 流程图,能口述一次「step = 一次模型请求 + 它调的工具,turn = 零或多个 step,先 claim 输入再 assemble……」;能说出「Model-visible ⟺ logged」为什么是铁律。

## 阶段 4 · 事件与能力缝(Capability Seams)(2 天)

**读:**
- `docs/event-producer-consumer.md`(每个事件的 producer/consumer 全表)。
- `docs/capability-seams.md`(能力图)—— **seam = Service Definition + Service Provider + Consumer,三者缺一不成 seam**。
- `docs/architecture.md` 的「Where new behavior goes」表 —— 这是「我要加 X,该挂哪」的速查。
- `docs/agent-lifecycle.md`(序列图)+ `docs/tool-execution-pipeline.md`。

✅ **验收**:能回答「为什么换一个 provider 就换掉整个产品行为?」;能说出 `fs/*`、`tools/*`、`telemetry/*` 这类能力事件和 `agent/*` 事件、`session/event` 有什么区别。

---

## 阶段 5 · 动手写第一个插件(1~2 天)

**读 cookbook(按需):**
- `docs/cookbook/extension-cookbook.md` —— feature → capability 的索引。
- `docs/cookbook/adding-a-package.md` —— 加一个包。
- `docs/cookbook/adding-a-tool.md` —— 加一个模型工具(含 UI 渲染意图 `generic/terminal/diff` 的前置设计)。
- `docs/cookbook/adding-an-llm-adapter.md` —— 加一个模型适配器。

**做:** 写一个能在 `--profile web` 下热更的工具,挂到 `ctx.tools`;再到 `ctx.llm` 注册一个极小适配器。用 `pnpm run demo:cordis`(需要 key)观察它如何修改自己的运行时。

✅ **验收**:能 run 起来、工具出现在 `dump-config` 和模型提示词里,并能写一个对应的小测试(`packages/*/*/tests`)。

---

## 阶段 6 · 深入与规范(2~3 天,边做边查)

到这里你已经能干活,再补齐「这个仓库为什么长这样」背后的规则。

**读:**
- `docs/development.md` —— TS 双 aggregate(Host/Client)布局、构建顺序、CI 闸门、日常命令。**这是贡献者的工作手册。**
- `docs/defensive-patterns.md` —— 生命周期/并发/子进程/teardown 的防御写法。
- `docs/testing.md` —— 测试与快照政策;`test:coverage` 才是 CI 覆盖闸门。
- `docs/invariants.md`(subsystems 下)—— 运行时不变量的含义(「断言的是被拥有的关系,而不是服务/方法存在」)。
- `AGENTS.md`(根,和 `CLAUDE.md` 是同一个文件)—— 全部约定:包命名、ESM、注册即效果、事件用声明合并、切换判别式、不硬编码可调项、屏障类型等。
- 颗粒度参考:`docs/graph-atlas.md`、`docs/module-graph.md`、`docs/config-catalog.md`(已生成配置目录)、`docs/tool-catalog.md`。

✅ **验收**:能通过 `pnpm run lint`、`pnpm run typecheck`;对一个非平凡改动知道要写 **Agent Note**(`.agents/notes/` 有归档,不可改已归档的)并且常常要补快照。

## 建议的节奏

| 时间盒 | 阶段 | 产出 |
|---|---|---|
| 第 1 天 | 0 + 1 | 能跑起来,能说清 Cordis 五句话 |
| 第 2~3 天 | 1~2 | 教程做完,能自己拼一个最小 profile |
| 第 4~6 天 | 3~4 | 主干数据流能口述,事件表能查 |
| 第 7~8 天 | 5 | 一个能热更的工具 + 一个适配器 |
| 第 9 天+ | 6~7 | 熟悉规范,开始读真实 PR / 写 Agent Note |

> 全程建议用 `pnpm dsh --profile web --dump-config` 当「镜子」:每次读完一个子系统,回看 dump 里对应的 row,把抽象和实例对上。最重要的一句话记忆:**在这个 repo,读代码永远优先读官方文档(docs/)管线,它们和源码用 `type-equiv` 强一致。**
